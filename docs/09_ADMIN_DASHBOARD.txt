VAYRO — 09_ADMIN_DASHBOARD.txt
====================================
Phase 9 — لوحة الإدارة. هذا الملف يُبنى تدريجيًا مع كل جزء من Phase 9.
الجزء المكتمل حتى الآن: إدارة المستخدمين (حالة الحساب + الأدوار).

────────────────────────────────────────
1. نقاط النهاية (كلها تحت /api/v1/admin/users، تتطلب دور ADMIN أو SUPER_ADMIN
   كحد أدنى للوصول أصلًا، بالإضافة لصلاحية محددة لكل إجراء)
────────────────────────────────────────
GET    /admin/users                    — قائمة (بحث/فلترة بالحالة/صفحات) — يتطلب users.view
GET    /admin/users/:publicId          — تفاصيل مستخدم — يتطلب users.view
PATCH  /admin/users/:publicId/status   — تجميد/حظر/إعادة تفعيل — يتطلب users.freeze
POST   /admin/users/:publicId/roles    — منح دور — يتطلب users.manage_roles
DELETE /admin/users/:publicId/roles/:roleCode — سحب دور — يتطلب users.manage_roles

────────────────────────────────────────
2. الأدوار الافتراضية (seed.ts)
────────────────────────────────────────
SUPER_ADMIN — كل الصلاحيات تلقائيًا.
ADMIN       — users.view, users.freeze, providers.manage فقط. لا يملك
              users.manage_roles ولا settings.manage افتراضيًا.
SUPPORT     — users.view فقط (قراءة، بلا أي تعديل).
USER        — الدور الافتراضي لأي حساب جديد، لا يُمنح/يُسحب عبر هذه الواجهة.

────────────────────────────────────────
3. حمايتان مطبَّقتان في الكود (وليس فقط بالصلاحيات) — اقرأ قبل التعديل
────────────────────────────────────────
- منع تعديل الذات: لا يمكن لأي admin تجميد/حظر نفسه، ولا سحب SUPER_ADMIN من
  نفسه — حماية من القفل العرضي (lockout)، وليست حدًا يحتاج تجاوزًا روتينيًا.
- حماية من تصعيد الصلاحيات (privilege escalation): منح أو سحب دوري ADMIN أو
  SUPER_ADMIN يتطلب أن يكون الفاعل (caller) نفسه SUPER_ADMIN حاليًا — صلاحية
  users.manage_roles وحدها لا تكفي. بمعنى: حتى لو مُنحت هذه الصلاحية لاحقًا
  لحساب ADMIN عبر لوحة تحكم مستقبلية، لن يستطيع ترقية نفسه أو غيره لـ
  SUPER_ADMIN. هذا التحقق بالكود (AdminUsersService.assertCanManageRole)،
  وليس فقط بجدول الصلاحيات.

────────────────────────────────────────
4. ⚠️ فجوة معروفة ومفهومة: التجميد/الحظر لا يُبطل الـ access token الحالي فورًا
────────────────────────────────────────
الـ access token (JWT) عديم الحالة (stateless) — لا يُتحقَّق من حالة المستخدم
بقاعدة البيانات في كل طلب (JwtStrategy.validate() يثق بمحتوى الـ token فقط).
هذا يعني: مستخدم جُمِّد/حُظِر للتو يبقى بإمكانه استخدام الـ access token
الحالي حتى انتهاء صلاحيته الطبيعية (JWT_ACCESS_TTL، الافتراضي 15 دقيقة).

لماذا هذا ليس ثغرة فعلية خطيرة: **كل** عملية تحريك أموال حقيقية
(TransfersService، WithdrawalsService، StoreOrdersService) تُعيد التحقق من
الحالة الحية بقاعدة البيانات داخل نفس الـ transaction قبل أي حجز/خصم — هذا
موجود من قبل هذا الـ Phase أصلًا. أي نافذة تعرّض فعلية محصورة بالقراءة فقط
(مثل عرض الرصيد) لمدة أقصاها 15 دقيقة، وليست بتحريك أموال.

ما يفعله setUserStatus فعليًا عند التجميد/الحظر: يُبطِل كل الجلسات النشطة
(sessions.revokedAt) — يمنع الحصول على access token جديد عبر /auth/refresh —
لكن لا يوجد حاليًا آلية إبطال فوري (blocklist) للـ access token الحالي نفسه.
إن احتجت إغلاق هذه النافذة بالكامل مستقبلًا: يتطلب صيانة قائمة إبطال أو تقصير
JWT_ACCESS_TTL بشكل كبير — قرار معماري أكبر، لم يُتخذ هنا دون طلب صريح.

────────────────────────────────────────
5. التدقيق (Audit)
────────────────────────────────────────
كل تعديل (تغيير حالة، منح/سحب دور) يكتب سطرًا في audit_logs (الجدول موجود من
Phase 1، لم يُستخدَم قبل الآن): actorId، action، entityType، entityId،
before/after (JSON)، reason، ipAddress. لا واجهة لعرض هذا السجل بعد — سيُبنى
مع باقي لوحة الإدارة.

────────────────────────────────────────
6. ما تبقى من Phase 9 (لم يُبنَ بعد)
────────────────────────────────────────
Providers management UI (تفعيل/تعطيل + مفاتيح من الواجهة بدل السكربتات)،
Store management (CRUD منتجات/فئات/ProviderService بدل seed.ts)، لوحة مراجعة
العمليات الغامضة (AMBIGUOUS_OUTCOME)، Exchange Rates، Fees، Limits، KYC،
Dashboard الرئيسي (إحصائيات عامة).
